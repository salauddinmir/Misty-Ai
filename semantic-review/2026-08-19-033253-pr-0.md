# Causal cognition wiring with durable learning and inspectable grounding

This change routes recall and association output into REASON, carries a selected answer through PLAN, adds workspace provenance to chat responses, isolates pre/post web-learning evaluation in cloned brains, and expands startup/shutdown persistence. It also aligns deployment dependencies and strengthens benchmark execution. **Watch for:** **confirmed, high** — ACT can return a lower-confidence fact than REASON selected while publishing inflated confidence and no evidence; **confirmed, high** — benchmark traffic can durably reinforce procedures through the class-wide persistence hook; **confirmed, medium** — hydration silently drops semantic facts older than the newest 10,000 episodes; **confirmed, medium** — learned weight changes on hydrated relations are never written back. The full Python 3.12 suite passes (840 tests), but it does not exercise these new causal and lifecycle paths.

**Verdict**: NEEDS_CHANGES

## High-level view

REASON now ranks recalled semantic and graph candidates and PLAN carries the winner, but ACT still invokes the legacy lookup handlers first and consults the ranked winner only after a low-confidence failure. A supported query can therefore answer from insertion order rather than reasoning order, defeating the intended REASON → PLAN → ACT dependency and making the new grounding contract inaccurate.

The pre/post assessor freezes a case set and applies only committed web-learning records to an evaluation clone. Procedure reinforcement is dispatched through a class-level `Procedure.reinforce` hook, however, so clone evaluation schedules database writes under the same durable procedure IDs and leaks synthetic benchmark behavior into production persistence.

Startup now restores semantic facts and indexes pre-existing graph records, while shutdown drains a unified managed task set before closing the database. The hydration query is capped at 10,000 newest episodes, and the relation index treats loaded edges as permanently persisted even after Hebbian learning changes their weights, leaving two durability gaps.

For conflicting answers, grounding reports `direct_knowledge` with no evidence IDs even though the workspace contains both candidate facts. This makes the newly exposed API metadata disagree with the decision path.

## ACT bypasses the answer selected by REASON

**Confirmed, high.** REASON sorts recalled candidates by confidence at `brain/core/brain.py:1563`, and PLAN carries the selected candidate. ACT reads it at `brain/core/brain.py:1710` but immediately calls `_act_query` or `_act_query_what` at lines 1717-1719. Those handlers select from memory using their own insertion/order rules; the reasoned candidate replaces their output only when the handler confidence is at most 0.35 (`brain/core/brain.py:1754-1760`).

A probe with `Alice --creator_of--> Widget` at confidence 0.2 inserted before `Bob --creator_of--> Widget` at confidence 0.99 produced `Alice`, even though REASON ranked Bob first. ACT then returned hard-coded confidence 0.9 and the final grounding payload contained `grounding_source: direct_knowledge` but no evidence source or ID, while the workspace exposed both the 0.2 and 0.99 records. The selected candidate must become the executable query action, or the legacy handler must accept the selected candidate and return the exact evidence IDs and confidence it actually used.

Perturbing `selected_answer` while keeping the same memory does not change a successful ACT result; the dependency is metadata/fallback-only rather than causal. The README’s causal behavior claim is therefore stronger than the implementation.

## Assessment clones leak procedure reinforcement into durable state

**Confirmed, high.** `_evaluation_clone` deep-copies procedural memory into baseline and post-learning brains (`brain/learning/post_learning_loop.py:160-201`), but API startup replaces `Procedure.reinforce` on the class at `apps/api/main.py:194-200`. Every matching procedure encountered during benchmark execution calls that global hook from `brain/core/brain.py:1539-1541`, which schedules `save_procedure` for the cloned object under the live procedure’s ID.

A probe with one `হ্যালো` procedure left the live in-memory procedure at use count 0 and strength 0.5, while baseline preparation invoked the hooked reinforcement three times on its clone, reaching use count 3 and strength 0.65. Under the production hook those synthetic values are written to the application database and can overwrite the real procedure on restart. Assessment needs an explicit no-persist/no-learning execution mode, or procedure persistence must be instance-scoped rather than a class-wide monkey patch.

The changed tests verify that an assessment record exists and that no-op runs do not claim improvement, but they do not run inside application lifespan with procedure persistence enabled. That is why all Phase 37 tests pass while durable isolation remains broken.

## Semantic hydration has an undocumented 10,000-episode horizon

**Confirmed, medium.** Startup loads semantic facts through `database.load_episodes(limit=10000)` at `apps/api/main.py:73`. `load_episodes` returns newest records first, so once the shared episodes table exceeds that limit, older semantic-fact episodes are absent from both `persisted_fact_keys` and semantic memory after restart. The table also stores non-fact consolidation episodes, which consume the same limit and can evict facts sooner than 10,000 learned facts.

Semantic facts need their own durable table/index or a paginated/type-filtered restore that does not silently truncate knowledge; if bounded hydration is intentional, the API and documentation need to expose that retention policy.

## Hydrated relation learning remains memory-only

**Confirmed, medium.** Startup records every loaded edge in `persisted_relation_keys` (`apps/api/main.py:67-71, 205-207`). Chat persistence saves only relation keys absent from that set (`apps/api/routes/chat.py:146-167`). Hebbian updates can change a loaded edge’s in-memory weight through its persistent relation ID, but no database update is scheduled for edges already in the index, so restart restores the old weight.

Durable plasticity needs dirty-edge tracking plus an update/upsert path. A restart test should strengthen a hydrated edge, drain managed writes, restore into a new brain, and assert the learned weight survives.

## New lifecycle paths have no direct regression coverage

**Confirmed, low.** The Python 3.12 suite passes all 840 tests, and Ruff reports all checks and formatting clean. Repository tests contain no references to the new persistence indexes/task set, causal `selected_answer`/`used_evidence_ids` flow, committed-delta evaluation brain, or assessment status fields. Add focused tests for competing-confidence query facts, exact multi-fact evidence attribution, first-turn persistence followed by restart, shutdown draining, durable procedure isolation during assessment, and relation-weight round trips.
